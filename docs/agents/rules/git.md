# Ветки, коммиты и Git

- Перед работой проверь `git status --short --branch` и remote. Не перезаписывай чужую работу.
- Новую задачу начинай от актуальной `origin/main`: `git fetch origin`, затем
  `git switch -c feature/SCRUM-123-add-room-filter origin/main`.
  Делай это при чистом рабочем дереве; не используй автоматический stash/reset.
  Если сеть недоступна, явно укажи, что база не обновлена.
- Если уже работаешь в ветке этой задачи, продолжай её. Не создавай ветку на каждый запрос.
- Формат: `<type>/SCRUM-<number>-<slug>`. Slug — краткий английский kebab-case;
  ключ Jira в верхнем регистре, номер — реальный номер задачи.
- Типы: `feature` — новая возможность; `bugfix` — исправление;
  `hotfix` — срочное исправление релиза; `refactor` — изменение структуры;
  `chore` — инструменты/зависимости; `docs` — документация; `test` — тесты.
- Примеры: `bugfix/SCRUM-124-fix-dice-selection`, `docs/SCRUM-125-update-setup`.
  Slash обязателен и для `bugfix/`.
- Если тикет не предоставлен и работа может быть выполнена по поручению пользователя,
  используй `<type>/no-ticket-<slug>`, например `chore/no-ticket-agent-harness`.
  В PR укажи причину; не создавай фиктивный ключ. Когда тикет появится, привяжи его
  к PR; опубликованную ветку не переименовывай без необходимости.
- Одна ветка/PR — одна связная задача. Для `hotfix` от release-ветки сначала проверь
  фактический релизный процесс; наличие такого процесса сейчас не подтверждено.
- Коммиты — небольшие и законченные. Формат: `fix(SCRUM-124): исправить выбор кубика`.
  Типы коммитов: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`.
  Без тикета: `chore: добавить инструкции для агентов`.
- Перед коммитом проверь `git diff` и `git diff --cached`; добавляй только нужные файлы.
- Не коммить build/dist, node_modules, tsbuildinfo, .env и локальные данные.
  Уже отслеживаемые артефакты не удаляй массово в несвязанной задаче.
- Не работай прямо в `main`, не делай force-push/reset --hard и не меняй историю
  чужих коммитов без явного поручения. Push/merge выполняй в рамках данного разрешения.
- Перед push проверь remote (`git remote -v`). При `403` / `Permission denied` /
  `Permission to ... denied` остановись: сообщи аккаунт, URL remote и текст ошибки.
  Не меняй `origin` самовольно и не выдумывай другой remote.
  Дальше: владелец репозитория выдаёт collaborator с правом push, либо сделай fork
  на свой аккаунт, запушь ветку туда и открой PR в `Krek0204/Sabacc`.
