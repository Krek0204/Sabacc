# Jira и GitHub PR

## Перед реализацией

- Jira-проект: `SCRUM`, [доска](https://isa-sabacc.atlassian.net/jira/software/projects/SCRUM/boards/1).
- Прочитай описание, критерии приёмки, комментарии и зависимости конкретной задачи.
  При отсутствии доступа используй переданный пользователем текст, явно отметь ограничение.
  Запроси недостающие сведения только если они блокируют решение; продолжай независимую работу.
- Сформулируй ожидаемый результат и способ проверки. Не выдумывай номера, требования,
  названия статусов или соответствие пунктов `Bugs.md` тикетам Jira.
- При конфликте требований задай предметный вопрос до изменения спорного поведения.

## Во время работы

- Сохраняй ключ задачи в ветке, коммитах и PR согласно [git.md](git.md).
- Новую независимую проблему опиши отдельно; создание тикета и комментариев в Jira
  выполняй, когда это входит в поручение. Не расширяй задачу молча.
- Статус Jira меняй только в рамках разрешённого workflow: сначала прочитай доступные
  transitions и условия. Не предполагай, что `In Progress`, `Review` или `Done` существуют.
- Ссылки Jira/GitHub не означают, что интеграция, синхронизация или права настроены.
  Не проси вставлять API-токены в чат или репозиторий; используй настроенную авторизацию.

## Подготовка PR

- Репозиторий: https://github.com/Krek0204/Sabacc ; база по умолчанию `main`.
- Заголовок PR (обязательный формат, иначе merge blocked CI `PR title`):
  `SCRUM-24 Исправить falsy-проверки для значения 1 на кубиках`
  - ключ Jira капсом в начале: `SCRUM-<номер>`;
  - пробел;
  - краткое описание с заглавной буквы, одна строка, до 100 символов.
  Без тикета такой PR не проходит gate; сначала заведите задачу или согласуйте исключение.
- Ветка не должна отставать от `main`: иначе падает CI `Up to date with main`
  (нужен rebase). На `main` также включён GitHub strict up-to-date, когда защита настроена.
- Используй [шаблон PR](../../../.github/pull_request_template.md).
- Приложи полную ссылку `https://isa-sabacc.atlassian.net/browse/SCRUM-123`;
  запись `Closes SCRUM-123` сама по себе не гарантирует закрытия Jira.
- Опиши проблему и изменение поведения, проверки с результатами, ограничения и риски.
  Для видимого UI приложи снимки, если среда позволяет воспроизвести сценарий.
- До передачи на ревью проверь критерии приёмки, diff и changelog.
  Если часть критериев/проверок не выполнена, явно укажи это; используй draft PR,
  когда создание PR поручено, но работа ещё не готова к ревью.
- При поручении публикации отправь ветку и создай PR; без него подготовь описание локально.
  Если push невозможен (нет прав, `403`), подготовь тело PR по шаблону локально,
  сдай пользователю блокер и варианты из [git.md](git.md); не меняй remote самовольно.
  Merge, релиз и закрытие тикета не следуют автоматически из создания PR.
- После разрешённого merge проверь факт слияния; переход Jira к завершению делай
  только при выполнении критериев и наличии разрешения. Сообщай фактические ссылки и статус.
