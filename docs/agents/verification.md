# Запуск и проверки

Команды взяты из конфигурации репозитория. Это инструкция, а не отчёт об успешном запуске.
Наличие команды здесь не означает, что она успешно выполнена; фактический результат
каждой затронутой проверки фиксируй в PR. Исторические срезы — в
[verification-history.md](verification-history.md).

Выполняй проверки по затронутым областям и сообщай фактический результат каждой.

## Frontend

Рабочая директория: `frontend/`. Нужны Node.js/npm, совместимые с lock-файлом и Vite 5
(README указывает Node.js 18+; точная версия менеджером версий не закреплена).

```sh
npm ci
npm run lint
npm run test -- --run
npm run build
```

`--run` завершает Vitest без watch-режима. Для локального UI — `npm run dev`.
Для изменения только документации установка зависимостей и сборка приложения не нужны.

`npm run lint` на существующем коде падает (десятки ошибок). Зелёный lint не является
критерием готовности, пока задача не про lint или явное исправление линта.
В отчёте укажи факт запуска или ошибку; не чини массу существующих замечаний попутно.

## Backend

Рабочая директория: `backend/`; JDK 21, wrapper `./gradlew`.
Проверь активный `java -version`; выбор JDK описан в [local-setup.md](../how-to/local-setup.md).

```sh
./gradlew test
./gradlew build
```

`SabaccApplicationTests.contextLoads` поднимает Spring-контекст: нужны доступная
PostgreSQL и настройки приложения. Для локальной БД переопредели
`SPRING_DATASOURCE_DATABASE_HOST=localhost`; остальные реквизиты должны совпадать
с локальным Compose. Настройки брокера находятся в `application-prod.yml`:
базовый профиль не является подтверждённым рабочим окружением полного приложения.
Не подключай тесты к рабочей пользовательской БД и не отключай их ради зелёного отчёта.
Зависимость теста от окружения и отсутствие исполняемых тестов ядра отмечай отдельно.

## Стек и ручная проверка

Из корня: подготовь локальный `.env` из `.env.example`, собери `frontend/dist`,
затем используй `docker compose --env-file .env up --build`, как описано в README,
или `./scripts/dev.sh up`. Команда запускает сервисы и пишет данные БД.
Для проверки конфигурации без запуска:
`docker compose --env-file .env config --quiet` (нужны Docker Compose и `.env`).
Не выводи развёрнутую конфигурацию с секретами в отчёт.

Для API/WebSocket/UI изменений проверь на локальном стенде:

1. Два независимых браузерных сеанса, разные имена игроков.
2. Создание комнаты, вход второго игрока и старт.
3. Ход и получение обновления обоими клиентами; отклонение недопустимого хода.
4. Затронутые задачей раунд/жетон/кубик и корректность итога.
5. Обновление страницы, отключение и возврат, если затронут жизненный цикл.

Известные несогласованности dev proxy описаны в [контексте](project-context.md).
Ручной сценарий — цель проверки, не утверждение, что все эти функции сейчас исправны.
Если окружение не даёт выполнить шаг, укажи блокер и выполненные независимые проверки.

## Документация и завершение

- Проверь локальные Markdown-ссылки, названия файлов и соответствие команд конфигам.
- Выполни `git diff --check`, посмотри `git diff` и `git status --short`.
  Новые untracked-файлы тоже проверь: обычный `git diff` их не показывает.
- Для приложения выбирай проверки затронутых областей; для общих контрактов — обе стороны.
- Зафиксируй новые ошибки отдельно от существующих; не называй проверку успешной,
  если она не запускалась или завершилась ошибкой.
