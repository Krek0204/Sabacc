# Серверный стенд Sabacc

Для учебного проекта с MAU около 100 достаточно одного Linux VPS и Docker Compose v2.
Начальная заявка: **2 vCPU, 4 ГБ RAM, 25–30 ГБ SSD**, один публичный домен и HTTPS.
Это предварительная оценка, а не результат нагрузочного теста. Рабочая гипотеза —
2–10 одновременных игроков (1–5 партий); MAU сам по себе не задаёт пиковую нагрузку.
Выделенные БД, Kubernetes, Prometheus/Grafana для такого стенда не требуются.

## Что передать девопсу

- Три контейнера: Java 21 / Spring Boot, PostgreSQL 14, Nginx со статикой React.
- Лимиты runtime: backend 1024 MiB (heap до 512 MiB), PostgreSQL 384 MiB,
  Nginx 128 MiB; суммарно 1536 MiB. Это ограничения, не измеренное потребление.
- Остальная память нужна ОС, Docker, файловому кешу и сборке. Лимиты runtime
  не ограничивают Gradle/npm при сборке: на 4 ГБ следить за пиком, при нехватке
  собирать образы на другой машине той же архитектуры или временно увеличить RAM.
- Порты: 80/443 на внешнем TLS reverse proxy; приложение по умолчанию доступно
  только на `127.0.0.1:8088`. PostgreSQL и backend не публикуются на хосте.
- Проксировать HTTPS на `http://127.0.0.1:8088`, передавать Host, Upgrade/Connection
  для WebSocket, таймаут чтения не меньше часа. Разрешить входящие 80/443 и SSH.
  Текущий вариант рассчитан на внешний proxy на том же хосте; контейнерный proxy
  требует отдельно согласовать сеть и адрес upstream.
- Постоянные данные: named volume `sabacc-server_postgres-data`; ежедневный `pg_dump`,
  копию хранить вне VPS. Логи Docker ротируются: до 3 × 10 МБ на сервис.
- Игра анонимная: существующий backend разрешает запросы без аутентификации.
  Origin ограничивает браузерные запросы, но не заменяет авторизацию.
  Это учебный игровой стенд; найденные игровые дефекты перечислены в `Bugs.md`.

## Подготовка и запуск

Использовать самостоятельный `docker-compose.deploy.yaml`, **без** локального Compose.
Его отдельное имя проекта/volume не затрагивает локальный `postgres-data/`.
На сервере не нужны Node.js и JDK — сборка выполняется в Docker.

1. Получить согласованный commit ветки и записать SHA для релиза.
2. Если `.env` ещё нет, скопировать `.env.example`. Существующий файл не перезаписывать.
   Установить случайный `POSTGRES_PASSWORD`, `APP_ORIGIN=https://ваш-домен`
   (без завершающего слэша), `RELEASE_TAG=<SHA>`. Ограничить доступ: `chmod 600 .env`.
   Не выполнять `source .env`: cron содержит пробелы.
3. Убедиться, что настроены TLS proxy и DNS. Затем из корня репозитория:

```sh
docker compose --env-file .env -f docker-compose.deploy.yaml config --quiet
docker compose --env-file .env -f docker-compose.deploy.yaml build
docker compose --env-file .env -f docker-compose.deploy.yaml up -d --no-build --wait --wait-timeout 180
docker compose --env-file .env -f docker-compose.deploy.yaml ps
curl --fail http://127.0.0.1:8088/api/v1/room/all
```

`up` ждёт готовности PostgreSQL, затем backend (Actuator health), затем Nginx.
Health endpoint не проксируется наружу. Frontend находится внутри `sabacc-web:<SHA>`;
монтировать `frontend/dist` на сервер не нужно. Внешний доступ проверить по HTTPS:
главная страница, список комнат и `/game/info`, затем две независимые браузерные
сессии: создать комнату, войти, начать игру, сделать ходы, оставить соединение
без ходов больше минуты и продолжить. Полный сценарий — [verification.md](../agents/verification.md).

Изменение пароля в `.env` не меняет пароль уже созданной БД; для действующей базы
изменять его отдельно и согласованно. `restart` не лечит unhealthy автоматически:
при проблемах смотреть `ps`, `logs --tail=100`, свободную память/диск и OOM.
Не пересылать необработанные логи приложения: в них могут быть данные игроков.

## Замер ресурсов перед выбором тарифа

Нужны работающий Docker и Python 3. Скрипт не создаёт игроков и не генерирует нагрузку:
он собирает CPU, RAM, сетевые/дисковые счётчики и число процессов для трёх сервисов.
Он не читает `.env` в отчёт и не выгружает логи приложения.

1. После запуска дать JVM прогреться 2–3 минуты.
2. Без игроков снять 5 минут простоя:

```sh
python3 scripts/measure-resources.py --output logs/resources/idle
```

3. Повторить во время реальной игры двух игроков (10 минут):

```sh
python3 scripts/measure-resources.py --samples 120 --output logs/resources/two-players
```

4. Если команда может собрать 10 игроков, повторить для пяти одновременных партий.
   Записать фактические число игроков/партий, действия и ошибки. Два игрока не
   подтверждают работу при десяти; HTTP-запросы списка комнат не заменяют STOMP-ходы.
5. Передать девопсу `summary.md`, `metadata.json`, `container-states.json`, `samples.jsonl`
   из каждого каталога. Каталоги создаются один раз; для повтора указать новое имя.

Для локального серверного стенда можно временно передать
`APP_ORIGIN=http://localhost:8088` в окружении команды Compose и открыть этот адрес.
Для замера уже запущенного обычного локального Compose:

```sh
python3 scripts/measure-resources.py --compose docker-compose.yaml --output logs/resources/local
```

Его конфигурация и лимиты отличаются от серверных — обязательно указать это при сравнении.
Docker Desktop измеряет контейнеры в Linux VM. Замеры не включают память ОС VPS,
сборку образов и короткие пики между снимками; финально проверить на Linux-сервере.
Если есть перезапуск, остановка или OOM, скрипт сохраняет сырьё, но завершает замер
ошибкой. Лимиты повышать по наблюдениям, а не по MAU.

## Обновление, резервная копия и откат

Обновлять вне активных партий: состояние игры хранится в JVM и теряется при рестарте.
Перед обновлением выполнить резервную копию (файл содержит данные игроков, не в Git):

```sh
mkdir -p backups
chmod 700 backups
docker compose --env-file .env -f docker-compose.deploy.yaml exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/sabacc.dump
```

Проверить успешный exit code, непустой файл и читаемость архива через `pg_restore --list`;
периодически проверять восстановление в отдельной тестовой БД. Копировать архив вне VPS.
Хранить предыдущие SHA исходников и образы, не перезаписывать тег выпущенного релиза.
Собрать новый `RELEASE_TAG` и выполнить `up --no-build --wait` из новой версии исходников.
Для отката вернуть checkout предыдущего релиза (включая `app.conf` и Compose),
в `.env` — предыдущий `RELEASE_TAG`, затем выполнить `up -d --no-build --wait`.
Не запускать повторную сборку старого тега поверх сохранённых образов.
При несовместимой миграции сначала согласовать восстановление БД из копии;
откат образа не откатывает схему Flyway.

`down` сохраняет named volume, `down -v` удаляет БД — не использовать для обновления.
Команда бэкапа перезаписывает `backups/sabacc.dump`: для регулярных копий использовать
отдельные имена с датой. Каталог исключён из Git.
