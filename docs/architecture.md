# Базовая архитектура

Sabacc — монорепозиторий браузерной Kessel Sabacc для двух игроков.
Ниже описана структура кода, изученная 2026-09-30. Подробные игровые требования —
в [Project.md](../Project.md), известные расхождения — в [Bugs.md](../Bugs.md).

## Компоненты

Браузер обращается к Nginx на порту 80. Nginx отдаёт React SPA из `frontend/dist`
и проксирует HTTP и игровые соединения в Spring Boot на внутреннем порту 8080.
Backend использует PostgreSQL на 5432. В полном Compose наружу опубликован только порт 80.

Frontend — React/TypeScript/Vite. `app` связывает router/store/providers,
`pages` содержит экраны, `widgets` — крупные UI-блоки, `features` — Auth/Game,
`entities` — Room/GameCard, `shared` — API, hooks и общие компоненты.
RTK Query обслуживает HTTP; STOMP поверх SockJS доставляет игровые события.

Backend сочетает Java-сервисы Spring и Kotlin-ядро. Пакеты `user` и `room`
управляют пользователями и комнатами; `game/session` связывает транспорт и сессию;
`game/messaging` и `ws` доставляют события; `system` содержит конфигурацию,
ошибки и события приложения. `gamecore` реализует карты, игроков, ходы и раунды.
Границы ядра представлены интерфейсами `IGameSession`, `IGameSessionFactory`,
`IGameMessageExchanger`.

## Поток партии

1. Клиент создаёт анонимного пользователя через REST `/api/v1/users/...`.
2. Игрок создаёт комнату или присоединяется через `/api/v1/room/...`.
3. Клиент открывает SockJS `/game?playerId=...&sessionId=...`.
4. STOMP-ход отправляется в `/app/input/session/{sessionId}/turn`.
5. Сервер обрабатывает ход и отправляет события принятого хода, ошибок, прогресса,
   результатов раунда и партии; клиент обновляет UI.
6. Текущее состояние также запрашивается через REST
   `/api/v1/room/game/current-state?sessionId=...`.

Это описание пути данных, а не гарантия корректности всех игровых переходов.
Имена destinations находятся в `WebSocketApiEndpoint.java`, REST-префиксы —
в `RestApiEndpoint.java`; клиентские обработчики — в `shared/lib/hooks` и `features/Game`.
Изменение DTO, enum или destination требует проверки обеих сторон.

## Хранение и жизненный цикл

PostgreSQL содержит пользователей, комнаты и таблицу сообщений чата. Flyway-миграции
лежат в `backend/src/main/resources/db/migration`; JPA валидирует схему.
Таблица чата сама по себе не означает, что реализован пользовательский чат.

Состояние активной партии хранится в JVM, а не восстанавливается из PostgreSQL.
Перезапуск backend прерывает активные партии; резервная копия БД не сохраняет их.
Локальная БД монтируется в `postgres-data/`. Изменение пароля в `.env` не меняет
автоматически пароль уже инициализированной базы.

## Ограничения и развитие

Полный Compose — текущая конфигурация локального стенда. Он не описывает законченный
production-процесс: HTTPS, релизы, резервное копирование и откат требуют отдельной настройки.
В конфигурации prod остались адреса предыдущей команды. Переменная `PUBLIC_IP`
передаётся контейнеру, но в изученном коде не найдена привязка, заменяющая эти origins.

Идентификатор в localStorage не доказывает авторизацию на сервере. Состояние рук,
проверка инициатора хода и жизненный цикл соединений требуют внимания при изменении игры.
Проблемы dev proxy и тестового окружения описаны в [диагностике](how-to/troubleshooting.md).

При изменении этой схемы обновляй также [контекст агентов](agents/project-context.md).
Детали устройства, потоков и хранения — в этом файле; пути поиска, контракты и
pitfalls для агента — в context.
