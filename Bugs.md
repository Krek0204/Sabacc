# Баги и критические ошибки — Kessel Sabacc

Проверка по состоянию кода в этом репозитории (ветка `Nikita_C`). Сверялось с правилами и требованиями из `Project.md` (версия 0.7.5).

Условные обозначения серьёзности:

- **Critical** — ломает партию, экономику, вскрытие или позволяет читерить / зависнуть сессии
- **High** — правило не выполняется, ключевой сценарий не работает
- **Medium** — жетон/UX/состояние работают неверно, но партия обычно доигрывается
- **Low** — косметика, мёртвый код, риск при нетипичном сценарии

## Critical

### C1. Банк раунда уничтожается, победитель не забирает банк

**Где:** `backend/src/main/kotlin/ru/ngtu/sabacc/gamecore/game/session/GameSession.kt` — `roundResults()`, примерно строки 657–686.

**Что происходит:** победитель получает только свои `spentChips` (возврат собственного налога). Затем с проигравшего снимается дополнительный налог (`forcePay` по разнице руки), после чего **оба** `spentChips` обнуляются. Фишки проигравшего из банка никуда не переходят.

**Ожидание:** победитель раунда забирает **весь банк** (налоги обоих игроков).

**Почему критично:** суммарное число фишек в партии падает каждый раунд. Победа раунда почти не награждает фишками соперника. Условие победы «лишить соперника фишек» работает через исчезновение фишек, а не через банк.

Дополнительно лог пишет, что победитель «платит» `handRating.first` — это не соответствует коду.

---

### C2. Победитель раунда не ходит первым в следующем

**Где:** `GameSession.kt` — `nextRound()`, строки 730–746.

**Что происходит:** итератор всегда создаётся заново по `players.keys` (порядок вставки: хозяин комнаты, затем второй). Победитель раунда никуда не переставляется.

**Ожидание:** первым в следующем раунде ходит победитель предыдущего.

**Почему критично:** преимущество первого хода навсегда закреплено за создателем комнаты.

### C3. Выбор 3 жетонов из 13 на сервере не существует

**Где:**

- `backend/src/main/kotlin/ru/ngtu/sabacc/gamecore/player/Player.kt` (строки 10–24) — в конструкторе сразу все 13 жетонов
- `GameSession.kt` — `SELECT_TOKEN` есть в `waitingForMoveType`, но в `tryMakeTurn` попадает в `else -> return` (строка 178); `requestTokenSelection()` (808–824) нигде не вызывается
- `frontend/src/pages/GamePage/ui/GamePage.tsx` — кнопка «Подтвердить» только закрывает модалку (`setIsModalOpen(false)`, строки 406–409), `handleSelectTokens` не вызывается; `client.send` / `client.userId` у STOMP-клиента нет

**Что происходит:** UI может показать выбор трёх жетонов, но сервер всегда считает, что у игрока все 13. Как только приходит `gameState`, эффект в `GamePage` (строки 76–89) **перезаписывает** `myTokens` серверным списком из 13 штук. На поле `GameTokens` режет список до `.slice(0, 3)` — на экране всегда первые три enum: `NO_TAX`, `TAKE_TWO_CHIPS`, `OTHER_PLAYERS_PAY_ONE`.

**Ожидание:** один раз выбрать 3 из 13; сервер хранит и проверяет только этот набор; жетон одноразовый на всю партию.

**Почему критично:** FR/UR по жетонам не выполняются. Через WebSocket можно сыграть любой из 13 жетонов.

### C4. Кубики: значение `1` ломает модалку (софтлок вскрытия)

**Статус:** исправлено в ветке `bugfix/SCRUM-24-fix-falsy-one-checks`
([SCRUM-24](https://isa-sabacc.atlassian.net/browse/SCRUM-24)) —
проверка `isDiceFace` (1–6), хуки вызываются до раннего `return`.

**Где было:** `frontend/src/features/Game/ui/GameDiceModal/GameDiceModal.tsx`:

```ts
if (!first || !second) return null;
```

**Что происходило:** в JS `1` — falsy. Если на кубике выпала единица, компонент возвращал `null`. Ранний `return` стоял **до** `useEffect` — при смене значений это ещё и нарушение Rules of Hooks.

Сервер в это время ждал `SELECT_DICE` (`GameSession.replaceImposterCard`).

**Ожидание:** показать оба значения 1–6 и дать выбрать кубик.

**Почему было критично:** при Самозванце партия могла навсегда застрять на вскрытии. Вероятность хотя бы одной единицы на двух кубиках — 11/36.

Тот же паттерн на картах — см. H10.

### C5. Фаза вскрытия не блокирует ходы (гонка со подсчётом)

**Где:** `GameSession.kt` — `nextTurn()` / `roundResults()` (строки 536–541, 676–698).

**Что происходит:** конец круга ходов не меняет `waitingForMoveType`. Через `CompletableFuture.runAsync { sleep(1s); processImposterCard() }` вскрытие откладывается, но `currentPlayerId` уже сброшен на первого игрока, а допустимые ходы всё ещё `PASS` / взятие карты / `PLAY_TOKEN`.

Игрок может взять карту или спасовать **во время** вскрытия и подсчёта. Повторный `pass` может снова вызвать `nextTurn` → повторный `roundResults`. Карты к этому моменту уже сняты `removeLast()`.

**Ожидание:** после третьего круга / двойного паса ходы запрещены до конца вскрытия и старта нового раунда.

**Почему критично:** порча рук, двойной подсчёт, падение на пустых списках карт.

Нет синхронизации: WS-поток и async-потоки пишут в одну `GameSession` без lock. `pause()` не останавливает уже запущенный async.

### C6. Состояние рук отдаётся обоим игрокам (и по открытому REST)

**Где:**

- `GameSession.getCurrentState()` — в DTO попадает `players.values` целиком, включая `sandCards` / `bloodCards` (строки 118–125)
- `GameSessionRestController.getCurrentState` — `GET /api/v1/room/game/current-state?sessionId=` без проверки, кто запрашивает
- `SecurityConfig` — `anyRequest().permitAll()`, CSRF выключен

**Ожидание:** карты соперника скрыты.

**Почему критично:** достаточно знать `sessionId`, чтобы подсмотреть обе руки. Ходы в STOMP тоже принимаются по `playerId` из тела сообщения, без сверки с handshake (`GameSessionWsController`, TODO на строке 18). Любой клиент может ходить за текущего игрока.

### C7. Двойной клик по кубику / два Самозванца → NPE

**Где:** `GameSession.replaceImposterCard` (строки 616–620); фронт `handleDiceSelection` не закрывает модалку сразу.

**Что происходит:** после первого `SELECT_DICE` поле `dice` становится `null`, но `waitingForMoveType` остаётся `SELECT_DICE` до следующего async-шага. Повторная отправка (двойной клик) заходит в ветку с `dice!![index]` → NPE, сессия может умереть.

Если на руке два Самозванца, второе вскрытие тоже идёт через эту ветку, пока `dice` ещё не брошены заново.

### C8. Ждущая комната закрывается как FINISHED при любом дисконнекте хоста

**Где:** `SessionRoomService.handlePlayerSocketDisconnect` (строки 261–274).

**Что происходит:** игра стартует только когда **оба** WebSocket подключены (`handlePlayerSocketConnection` + `SessionReadyEvent`). Пока второго игрока нет, `isPlayerSecondConnected` остаётся `false` (дефолт в `SessionRoom`).

Любой обрыв сокета хоста (SockJS сменил транспорт, heartbeat 10 с, nginx `location /game/` без длинного `proxy_read_timeout` — см. M19, повторный `deactivate` в `useWebSocketGame`) вызывает disconnect:

- хост: `isPlayerFirstConnected = false`;
- второго нет → `isPlayerSecondConnected` и так `false`;
- условие «оба offline» истинно → статус комнаты **FINISHED**, публикуется `SessionFinishedEvent`.

Повторный handshake в уже `FINISHED` комнату отклоняется (`JoinFinishedSessionException`). Соперник не видит комнату в `available-for-join` (там только `WAITING_SECOND_USER`).

**Ожидание:** пока второго игрока нет, обрыв хоста не должен финализировать комнату (пауза / ожидание реконнекта, а не FINISHED). NFR: проигрыш через ~15 с после дисконнекта относится к **идущей** партии.

**Почему критично:** по localhost сокет обычно не рвётся — «у себя работает». По сети ждущая сессия часто умирает до входа соперника. Пара не попадает в одну живую комнату, `GameSession` не создаётся.

### H14. Гонка матчмейкинга: два «Играть» → две комнаты, игроки не встречаются

**Где:** `useSetupRoom.ts` (строки 49–79); сервер — `getAvailableRoomsForJoin` + `createSessionRoom` без общей блокировки.

1. оба делают `leave/all` и ждут 1 с;
2. оба получают пустой `available-for-join`;
3. оба делают `POST /create`;
4. получаются **две** комнаты `WAITING_SECOND_USER`; каждый ждёт соперника в своей.

Если `join` в найденную комнату падает, `roomId` обнуляется и **создание своей комнаты не выполняется** — клиент зависает на «Создание комнаты...» без `sessionId`.

## Medium — жетоны и правила

### M1. Глобальные жетоны завязаны на иммунитет соперника

`IMPOSTERS_TO_SIX`, `SYLOP_TO_ZERO`, `COOK_THE_BOOKS` — эффекты на стол / ранги, не «удар по сопернику». Если у соперника иммунитет, эффект **не включается**, жетон всё равно удаляется из списка.

То же для направленных: `EXHAUSTION`, `DIRECT_TRANSACTION`, `EMBARGO`, `EMBEZZLEMENT`, `OTHER_PLAYERS_PAY_ONE`, `GENERAL_AUDIT` — при иммунитете no-op, жетон сожжён.

### M2. GENERAL_AUDIT смотрит на `passCount > 0`, а не на пас соперника

`isInPassState` выставляется в `pass()`, но для аудита не используется. У **первого** игрока круга `passCount` всегда 0 — аудит никогда не срабатывает. У второго срабатывает, если **кто угодно** уже пасовал в этом круге (в т.ч. принудительный пас от эмбарго).

Лог: фишки «добавлены в банк игрока»; код кладёт их в `opponent.spentChips` (и они сгорят в C1).

### M3. Эмбарго + пас заканчивают раунд раньше времени

Принудительный пас тоже делает `passCount++`. Пас игрока + эмбарго соперника = `passCount == 2` → раунд кончается, хотя «оба добровольно спасовали» не выполнялось.

`isInPassState` после последующего взятия карты в том же раунде не сбрасывается (сброс только в `nextRound`).

### M4. TAKE_TWO_CHIPS / EXTRA_REFUND только из своих `spentChips`

Если в этом раунде игрок ничего не платил, жетон даёт 0 фишек. Тексты UR/UI: «верните 2 фишки» / «верните 3 фишки, выплаченные в этом раунде». Для «Доп. возврат» привязка к выплатам логична; для «Возврат» — спорно, но при пустом личном взносе жетон бесполезен.

### M5. AUTO `IMPOSTERS_TO_SIX` не шлёт accepted-turn

Замена Самозванца на 6 идёт молча. UI может продолжать показывать Самозванца до следующего fetch.

### M6. Ничья по `(разница, сила)` не обработана

При равных `handRating` побеждает порядок в `players.values` (хозяин комнаты). Отдельного исхода «ничья» нет.

### M7. COOK_THE_BOOKS инвертирует сортировку пар, а не номиналы

Описание: «инвертировать ранги Sabacc». Реализация — `sortedWith(compareByDescending)`. Это меняет «кто лучше», но не зеркалит 1↔6. Может расходиться с задумкой алгоритма.

### M8. SYLOP_TO_ZERO: в логе текст от другого жетона

Строка ~449: «all Imposter cards will become 6».

При активном флаге `rateHand` кастит не-сайлоп к `ValueCard`. Если Самозванец по гонке не заменили — `ClassCastException`.

### M13. DIRECT_TRANSACTION кладёт в broadcast целые `Player`

`DirectTransactionInfo` содержит обоих игроков с руками. Сообщение accepted-turns видят оба клиента — лишняя утечка, тяжёлый payload.

### M14. `getSessionMembers` падает, если второго игрока ещё нет

`SessionRoomService.getSessionMembers`: `List.of(playerFirst, playerSecond)` — NPE при `playerSecond == null`.

### M15. Имя: нет верхней границы 12 символов, бэкенд не валидирует

UI: `length >= 4`, максимума нет. `CreateUserDto` без Bean Validation. Требование 4–12 символов не закрыто.

`checkSessionExpiration` объявлен в `authSlice` и нигде не диспатчится. Просроченный пользователь из `localStorage` остаётся «залогиненным» до ручного logout.

### M16. Ник соперника в списке комнат — неверный столбец

Таблица показывает `playerSecondId`. Для комнаты в ожидании второй пустой, для своей созданной комнаты «соперник» не отображается. Нужны имена, не внутренние id.

### M17. Конфиг брокера STOMP только в `prod`

`application.yml` не задаёт `websocket.broker.*`. `PropertyCheckApplicationContextInitializer` требует эти ключи. Локальный запуск **без** `SPRING_PROFILES_ACTIVE=prod` не стартует. Docker как раз использует `prod`.

### M18. CORS в `SecurityConfig` захардкожен на `http://localhost:5173`

`allowed-origin-patterns` из yaml не используются для origin. Через nginx (same-origin) обычно незаметно; прямой заход на `:8080` с продакшен-фронта — риск CORS.

### M19. Nginx `location /game/` беднее, чем `/ws/`

Нет `Host`, `proxy_read_timeout`, `Connection upgrade` настроен иначе. SockJS ходит на `/game/...`. Риск обрыва долгих партий на прокси; короткий обрыв хоста в очереди добивает комнату (C8).

### M20. Открытые разрушающие API

Без авторизации доступны создание/удаление пользователя, `DELETE` комнаты, `leave` за любой `userId` в query. Состояние игры только в RAM: рестарт backend убивает все партии (это ещё и расхождение с текстом архитектуры).

### M21. Юнит-тесты ядра выключены

`backend/src/test/kotlin/.../GameSessionTest.kt` целиком закомментирован. Регрессии C1–C5, жетонов и вскрытия автотестами не ловятся. На фронте по сути один тест `classNames`.
